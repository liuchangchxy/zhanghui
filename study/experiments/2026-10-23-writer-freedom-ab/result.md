# Writer Freedom A/B — 结果

**判定：`CURRENT_DESIGN_BETTER`**

先说结论，再说怎么得出的。

> 「强治理、弱干预」这版 Writer-facing 链路，在三个真实章节上**没有**写出更好的正文，
> 并且在两个关键控制点上出现了实质性退步。正式设计更好。
>
> 但这个否定结论里有一条更有价值的发现：**问题不在「干预变少」，在「材料变薄」。**
> 见第 5 节。

真正站得住的是方向的一致性（5/6 选择 + 多维度同向），不是任何单个数。

## 2. 控制力：退步，不是持平

两位评委独立发现 arm B 在两章上**改变了剧情事实本身**。这两处都不是文笔问题。

### ch7：钩子方向做反了

章纲要求「复算出的当夜潮位，比官方记录**低了**将近一米」。
arm A：复算 2.48 / 官方 3.42 → 低 0.94 米，方向正确。
arm B：复算 3.23 / 月报 2.31 → **高** 0.92 米，方向相反。

评委原文：

> 「Y 算出『三点二三减二点三一，零点九二』——复算比月报**高** 0.92 米，而钩子要求
> 『比官方记录**低了**将近一米』，方向反了。且这不是改一个数能修的。」

arm B 的 brief 里**写了**这个方向（「比官方记录低了将近一米」），但只写了一处。
arm A 的 brief 里这个方向出现 7 次（含具体数值）。Writer 在 B 里只看到一次，
随后在自己构造数字时把方向做反了。

**Reviewer 也独立判定了同一件事**，而且是本次唯一一条 arm B 的 `high` 级钩子问题：

> 「规划钩子为『复算出的当夜潮位，比官方记录低了将近一米』，而正文复算 3.23 米、
> 月报 2.31 米，复算值比官方记录高 0.92 米……hook 的方向被写反。」

### ch10：核心变化被换掉了

章纲要求「本章变化：注意到老周手抄本的**年份连续性**有缺口」。
arm B 写成：2016 年 3 月那一页「抄到十六日止、四月整页空白」——**日期空白**，不是年份断档。
两位评委都独立指出：「关键一拍没打准」「本章核心变化没落地」。

追到源头，问题出在 arm B 的 brief 本身：

> arm A brief：「年份不连续，中间少了一叠」
> arm B brief：「**年份是连续的**，可其中某一段是空的」

arm B 的 Context Agent 把「年份连续性有缺口」理解成了「年份连续、内容有空白」，
并在 brief 里写下了与章纲相反的表述。Writer 忠实地执行了这个错误表述。

这里要说清楚：**章纲原句「年份连续性有缺口」本身就有歧义**（是「年份不连续」还是
「年份连续但内容有缺口」）。arm A 押对了，arm B 押错了。这才是关键——
arm A 的五段任务书里这个说法出现多次、并被展开成「年份从 2016 排到 2026，
中间少了一叠，位置不对」，歧义在重复中被消解；arm B 只写一次，押错就一路错下去。

**这是本轮最重要的机制发现：把 Context Agent 的判断过程藏起来（改为内部工具）之后，
它对章纲的偏离失去了可见性。** 不是「藏起来导致想错了」，而是「藏起来导致想错了没人纠正」。

### 情节执行统计

| | arm A | arm B |
|---|---|---|
| 评委判定「关键节点全部落地」 | ch6 ✓、ch7 ✓、ch10 ✓ | ch6 ✓、ch7 ✗（方向反）、ch10 ✗（变化错） |
| 评委选它为好稿 | 5/6 | 1/6 |
| Reviewer 结构化问题（3 章合计） | **21** | 26 |
| 其中 high | **1**（ch6） | 6（ch7×3、ch10×3） |
| blocking | 0 | 0 |

Reviewer 的数量差不能当质量差读，原因有三：

1. **同一个错误可能只在一边被抓到。** ch7 的「旧报库位置」「清点单状态」两处漂移
   成因在 arm A 也存在，但 arm A 的稿子没写这些细节，所以没被触发。
2. **Reviewer 之间本身就松紧不一。** arm B 的 ch6 reviewer 只报了 2 个 low；
   arm A 的 ch6 reviewer 报了 1 个 high。
3. **arm B 的写作里可核对的细节更多**（见下面第 4 点），本身就会暴露更多可挑之处。

但有三条是**两个独立 reviewer 与两位 independent 评委都指向同一处**的，可以当硬结论：
ch7 钩子方向、ch10 缺口形态、ch10 第 9 章钩子断裂（正文完全没出现笔迹/照片/值班员，
第一场的动机只剩「划掉待办清单」）。

## 3. 为什么「减少干预」没有换来更好的正文

四个可验证的原因，按证据强度排：

### (1) brief 没有真的变短——有一章反而长了

| 章 | brief A | brief B | 差 | prompt A | prompt B | 差 |
|---|---|---|---|---|---|---|
| ch6 | 3875 | 3476 | −399 | 33133 | **26595** | −6538 |
| ch7 | 4114 | 2874 | −1240 | 33412 | **27032** | −6380 |
| ch10 | 3361 | **5188** | **+1827** | 30752 | 34392 | **+3640** |

新规格写的是「总长 1200–1800 汉字」，**三章全部超标**（3476 / 2874 / 5188）。
最该瘦身的一章（ch10，对峙+信息受限，最容易写成施工单）反而膨胀了 55%，
Writer 收到的 prompt 也比 arm A 长了 3640 字节。

**原因**：1200–1800 只是一句提示词，代码里没有任何校验。arm A 的旧格式反而因为
结构固定（五段、每段有界）而更稳定。**删掉结构之后，长度失控了。**

### (2) Router 的「一句话」没有做到

新规格：`chapter_guidance` 一句 40–120 字，上限 240。
arm B 实际输出：**11 条全部超过 120 字**（133–180 字），平均 160 字。

对比 arm A：137–178 字，平均 151 字。

**guidance 长度几乎没有变化。** 代码只在超过 240 字时截断并 warn，40–120 是软要求，
模型没有遵守。所以「Router 从编导退回选+说一句」这件事**在本次实验里没有真正发生**——
Router 仍然在写 160 字的段落，只是换了措辞。

### (3) Skill 原文进入 prompt，但把 prompt 撑大了

| 章 | arm A skill 段 | arm B skill 段 |
|---|---|---|
| ch6 | 815 字符 | **2033 字符** |
| ch7 | 633 字符 | **2868 字符** |
| ch10 | 651 字符 | **2596 字符** |

设计意图是对的（给原则，不给脚本），但结果是**每个 Skill 把 `## 方法` 的全部 5–8 条
加正反例全量塞进 prompt**。arm B 的 skill 段是 arm A 的 2.5–4.5 倍。

这构成一个直接的因果：**删掉了 Router 的动作脚本（约 150 字/条），换来了 Skill 原文
原则（约 600 字/条）。** 总干预量没有下降，只是从「具体指令」变成了「抽象原则」。
而抽象原则恰恰是评委说「规则太多」时指的东西——B 在「规则太多」上比 A 更差，
与此一致。

### (4) 附带观察：arm B 更爱写可核对的细节，因此更容易撞车

arm B 的 ch7 reviewer 找出 3 个 `high`，其中两个（旧报库位置、清点单状态）的根源
在 arm A 也存在，但 arm A 的稿子**根本没提这些细节**，所以没有被抓到。
arm B 因为被要求「只给原则、自己决定」，反而更主动地写具体地点、具体钟点、具体项数。
这提高了文本的可核对性，也提高了与既有 Canon 撞车的概率。

这不是本次能定论的东西（n=3），但值得记一笔：**减少指令不一定减少错误，
可能只是把错误从「执行不到位」换成了「自由发挥时撞设定」。**

## 4. 哪些确实按设计发生了变化

尽管结论是否定的，以下几项**确实生效了**，是未来可以保留的部分：

| 变化 | 证据 |
|---|---|
| Writer Package 不再出现 `CBN`/`CPNs`/`CEN` 术语 | ch7/ch10 全 0；**ch6 残留 3 次**，来自 Context Agent 自己在 brief 里写了「大纲里标作 CBN / CPNs / CEN」，渲染层没能拦 |
| 章节标题中文化（`## 1. 本章要完成的事` vs `## 1. 本章写作意图 (Current Intent)`） | 已生效 |
| 规划节点渲染为自然行，且动作不再丢失（修复后） | `许知远：用周期规律与邻站插值，得到当夜逐时潮位` |
| 原始 `{"event_type": ...}` JSON 转储被解包成自然语言 | arm B 无 JSON 转储，事实未丢 |
| `story_craft.path: value` 内部簿记不再进 prompt | 已生效 |
| Router 不再编具体动作/对白 | 检查三章 guidance：无「翻到照片，看一眼，滑走」类演出 |
| 受治理上下文逐字节相同 | `checksums.txt` 三章全 True |

也就是说，**「删掉规划术语和演出脚本」这部分成功了；
「压缩材料总量」这部分失败了，并且伤害了控制力。**

还要记一条反面证据，免得把第 1 节的红字读过头：

> arm B 的 ch6 有一位评委判 B 更好，理由是「X 把『信任的代价』落在动作上，
> 核心冲突不靠台词点破」——那条评委实际是在夸 B。也就是说 **lean 包确实能让 Writer
> 写出更克制的稿子**，只是这种收益在另外两章被控制力损失盖过了。
> 这不是「设计一无是处」，是「设计换来了某种东西，但代价更大」。

还有一条可量化的同向证据——**arm B 的篇幅更靠近 2000–2500 的目标**：

| 章 | arm A 汉字 | 是否超 2500 | arm B 汉字 | 是否超 2500 |
|---|---|---|---|---|
| ch6 | 2687 | 超 | 2638 | 超 |
| ch7 | 2916 | 超 | **2464** | 未超 |
| ch10 | 3098 | 超 | 2537 | 超 |

arm A 三章全部超出上限（均值 2900），arm B 只有两章轻微超出（均值 2546，低 12%）。
这说明**删掉「必须覆盖哪些节点」的清单之后，Writer 不再为了凑节点而灌水**。
代价是这些被删掉的节点里，正好包含着 ch7 的潮位方向。

顺带一提：两臂的长度都没有被硬约束住（`2000-2500` 在本框架里只是建议值），
所以这项差异是「材料密度」的自然后果，不是哪一臂更守规矩。

## 5. 真正的结论

本轮想要验证的假设是「减少创作干预 → Writer 写得更好」。结果否定了它，但同时
定位了更准确的原因：

> **失败不是因为「管得少」，而是因为「给得少」。**

arm B 的 Writer 在 ch7 把潮位差的方向做反、在 ch10 把「年份缺口」写成「日期空白」——
这两处都不是「自由发挥过头」，而是**材料里没有足够硬的事实把它钉住**。
arm A 靠同一句话在 brief、prompt、节点行里重复三四次，形成了一种冗余纠错；
arm B 把这些重复当成「过度设计」删掉了，于是单点错误没有第二道防线。

同时，arm B 并没有真的变得「轻」：brief 一章比一章长（最长 5188 字），
skill 段是 A 的 2.5–4.5 倍，Router guidance 长度不变。
**它只是把「具体的干预」换成了「抽象的干预」，总量还上升了。**

所以正确的下一步不是「继续减少干预」，而是三件更窄的事：

1. **给硬事实一个受保护的落点。** 章纲里「方向」「缺口类型」这种一错就毁掉整章的事实，
   需要一个不进 Lean 删除范围的结构化位置（现在 `_natural_node` 和 lean 渲染都会重写它们），
   而且这个位置要能抵抗章纲自身的歧义（ch10 的「年份连续性有缺口」就是例子）。
2. **限制 Skill 原文的体积。** `attach_skill_bodies()` 现在把 `## 方法` 全量附加（1200 字上限/条）。
   本次实测每章因此多出 1200–2200 字。要么只附 1–2 条最相关的，要么只附原则标题。
3. **给 brief 长度一个真的门。** 1200–1800 现在只是提示词，三章全部超标。
   要么加校验（超限 warn 或截断），要么承认这个数字是假的、改成「不超过原五段格式」。

这三条都属于「让材料更硬、更短」，不属于「减少治理」。

## 6. 诚实性说明

**第一轮 arm B 作废。** 我在 `_natural_node()` 里有一个数据丢失 bug，把所有
`主体 | 动作 | 结果` 节点渲染成 `主体：结果`，删掉了动作。那一轮的全部产物已归档到
`.tmp/wf-ab/_pre-fix/`，不参与本结论。详见 `03-renderer-bug-disclosure.md`。

**本轮结论只基于修好之后重跑的一轮。** 三章 arm B 全部从头起草。

**没有做的事**：没有手工调整任何一章的 Skill 组合；没有干预 Router 选择；
没有修改 Writer 的 draft；没有为了让 B 好看而重跑任何一章。

**一处需要澄清的指纹告警。** arm B 的 ch10 reviewer 在报告里指出
`review_subject_fingerprint` 与它本地复算值不一致，并建议提交前核验。
我复核了：`ingest` 记录的值 `3876463b…` 与框架 `prose_subject_sha256()`
对同一文件的复算结果**完全一致**；reviewer 的 `49b62578…` 是它自己另算的，是异常值。
**这不是数据问题，是 reviewer 用了不同的计算口径。** 但把它记在这里，因为
reviewer 主动报出自己复算不符这件事本身是对的。

**一处结论的边界。** 本次 n=3（三章、两名评委/章）。三章同向（5/6 选 A）
足以支撑「正式设计更好」，不足以支撑「任何 Lean 化改动都无益」。
被否掉的是**这一版**的实现方式，不是「弱干预」这个方向本身。
