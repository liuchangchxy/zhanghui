# 窄审计：Writer 前链路

审计范围只限「Writer 拿到什么」，不重新做全仓治理审计。证据来自 `82e496d`（PR #62 HEAD）
的真实产物，即 `study/experiments/2026-10-23-literary-skills-batch1-ab/` 里第 5 章的
sealed prompt 与 `creative_brief_0005.txt`。

---

## 1. Context Agent 最终替 Writer 做了哪些创作决定

第 5 章的 `creative_brief_0005.txt`（4,072 字）逐段核对：

| 已经替 Writer 决定的事 | 原文位置 |
|---|---|
| 开场先做哪件拖延的琐事 | 「开场他多半会先做一件毫无必要、却极其规范的琐事来拖延——把差异说明表重新誊一遍，把笔尖削好，把清单按编号重新排一次」 |
| 用哪三到四处物证、按什么顺序 | 「本期共几页的声明、页码跳号、装订孔位错开、残留的纸茬、相邻两页的记录衔接不上。任选其三，每一条之间隔一个动作：翻页、对着窗户的光看、量一下页边距、把册子侧过来看装订」 |
| 用哪个动作写情绪 | 「他有一个很自然的动作可以反复用：想抄下缺页的页码，笔停在纸上——抄下来，就等于承认这里有东西缺了」 |
| 场景四问逐题作答 | 「场景四问。」整段把 ①想得到什么 ②谁在挡 ③被迫做什么 ④什么变了 全部写死 |
| 结尾停在哪、停几次 | 「结尾就停在那行字上……写他看了多久，有没有伸手去摸一下，最后有没有把册子合上」 |
| 句式颗粒度 | 「不要堆五条，堆多了像验尸报告」「句长跟着他的手走」 |

**结论**：Context Agent 产出的不是材料，而是一份**镜头脚本 + 执行注意事项**。它把
「这一章必须发生什么」和「这一章应该怎么写出来」合并成了同一份文档，Writer 只需要誊写。

## 2. Creative Brief 里 Writer 真正必须知道的

只有五类：上章停在哪、本章必须发生什么（目标/阻力/代价/结束前的状态变化）、人物当前状态与
驱动力、绝对不能写错的事实与禁区、本章大致该是什么感觉。

`creative_brief_0005.txt` 里对应的内容约占全篇 35%。其余 65%（开场动作、物证清单、镜头顺序、
结尾姿势、句式要求）都是**可以下沉给 Writer 的创作自由**。

## 3. 哪些只是系统自己的思考过程

- **场景四问 / 追读三问的逐题作答**：本来是 Context Agent 的内部推理工具，被原样写成任务书章节。
  第 5 章的「场景四问。」段 1,797 字里，真正的信息（他其实想确认它没问题 / 挡住他的是册子本身 /
  结束时失去了「归档之后不会变」）约占 200 字，其余是推理过程的展开。
- **审查趋势**：「前两章都没有阻断项，但连续两章被提醒……上一次出现过记录写『开机』、正文只写
  『打开外壳』的偏差」——这是系统对历史审查结果的记忆，不是本章创作材料，却直接进了任务书。
- **逐字段复述**：`story_craft` 的伏笔链、限时锁、人物弧光、主题呼应原本已经在 governed context
  里，Context Agent 又把它们翻译一遍，Writer 拿到两份表述。

## 4. Writing Skill Router 当前做了什么

以第 9 章（round 2）的真实选择为例，`chapter_guidance` 共 1,129 字：

| 动作 | 证据 |
|---|---|
| 选了什么 | scene-sequel / pov-distance / character-agency / dialogue-subtext / information-gap（5 个，达上限） |
| 改写了什么 | 把 `pov-distance` 的原则「别人的内心只能从外部读」改写成三场戏的分场安排：「**第一场**：他进库房只想拿到……**第二场**：把『查笔迹』改写成『缩范围』……**第三场**：从人员名册上只取一个状态」 |
| 丢掉了什么 | Skill 自己的原则、正例、反例——全部丢掉，只留改写后的动作 |
| 新增了什么 | **原文没有的动作**：「翻到照片，看一眼，滑走，把手机扣在桌上」「问出口之前先想这一问会落在哪张纸上」「多翻了一册、多留了一笔记录」 |
| 制造了新的执行结构 | 「分三次用，一次只推进一层：第一次……第二次……第三次……」 |

`writing_skill_registry.py` 的 `THEORY_LEAK_TOKENS` 只拦 meta 词（`skill` / `理论` / `hook_type`），
**不拦「第一场/第二场」「第一次/第二次」这类执行序列**。所以越具体的编导越容易通过校验——
校验的方向和目标是相反的：它保证「不要出现理论名」，却不保证「不要替 Writer 编动作」。

对照第 9 章 B 稿的评委记录：Writer 用「一是／二是／三是／四是」列特征，被判「手法外露」。
**源头在 Router 的本章翻译，不在 SKILL.md。**（PR #62 自己也记下了这个判断，但当时的结论是
「停止调参」，没有动 Router。）

## 6. 重复与过度具体化清单

| 重复项 | 证据 |
|---|---|
| 本章目标 | 在 prompt 里出现 **4 次**（意图 / 场景四问①/ 追读三问 / Creative Brief） |
| 本章核心冲突 | 「归档之后不会变」出现 3 次、「职业信仰」出现 **7 次** |
| Scene 计划 | 章纲字段 → 场景四问 → Creative Brief 的「场景四问」段 → Router 的落地安排，**四层** |
| 追读链 | 追读三问 → Creative Brief 的「读者在等什么」段，**两层** |
| 伏笔 | governed canon 的事件 + Writer Context 的紧急伏笔 + Creative Brief 的「可以回看的旧线索」，**三层** |
| 原始 JSON 事件 | **1,560 字符**的 `{"event_type": "open_loop_created", ...}` 原样进 prompt |
| 路径转储 | **2,856 字符**的 `[{'path': 'story_craft.foreshadow_chain.0.buried_chapter', 'value': 3}, ...]` |
| 规划术语 | `CBN` / `CPNs` / `CEN`、`节拍位置：Debate`、`Progress Obligation` 直接暴露给 Writer |

合计：**14,598 字符的 prompt 里，约 6,000 字符（41%）是重复、术语或系统内部转储。**

## 7. 哪些最可能导致「像执行任务」

按嫌疑排序：

1. **Router 的动作脚本**（第 4 节）——直接给出动作和对白，Writer 逐字执行即「任务完成」。
2. **Creative Brief 的镜头顺序**——「先……再……，每一条之间隔一个动作」把叙事变成工序。
3. **场景四问逐题作答**——四问本意是让 Writer 自己判断，逐题作答后变成四个填空题；第 5 章
   「场景四问。」段里的「于是他被迫先做一件很档案员的事：给自己定判据——什么才算『不完整』，
   定完了再逐项去对」，被 Writer 执行成了编号判据小标题。
4. **规划术语与重复**——`CBN/CPNs/CEN`、41% 的重复率让 prompt 读起来像验收清单。

## 8. 审计结论

假设成立，但**比原假设更具体**：

> 问题不是「Context Agent 想得太清楚」，而是**同一份判断在到达 Writer 的路上被表达了四次，
> 并且其中两次（Context Agent 的镜头脚本、Router 的动作脚本）已经从材料变成了演出**。

因此最小修法是三处删减，而不是重写任何治理层：

1. Context Agent：四问/三问退回内部工具，只写结论；不再编动作、对白、镜头；
2. Router：退回「选 + 说一句为什么」，方法原文由 runtime 从 `SKILL.md` 原样附给 Writer；
3. Writer Package：去掉规划术语、重复的 Scene/Reader-Pull 问句块与原始事件/路径转储。
