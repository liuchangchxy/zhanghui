先给结论

六条判断，按证据强度排序。每一条都能在后文找到对应产物或代码行；不能落到证据的，已标为推断。

一、稳定可复现的差距是“阅读吸引力”，不是“文学质量”

Stage 3 的三章盲评里，章回的文学质量均值 4.333，高于 Jarvis 的 4.167；人物/世界一致性 4.167 对 3.833；跨章连续性 4.083 对 4.000。唯一稳定落后的是阅读吸引力：2.750 对 3.833，两两比较都落后约 1.5 分。评委给的理由是具体的：“整章停在登录之前”“近乎静止”“把心理写得细但耗在自我盘问上”。

证据：zhanghui-benchmark/runs/return-to-peak-001/STAGE3-REPORT.md 第五节。n=3，评委与 Writer 同为 deepseek-v4.1-flash，阅读吸引力存在 −1.5 / −1.67 / −0.17 的位置偏差，只能当方向性信号，不能当稳定排名。

二、章回不是“理论不够”，而是理论被放在了错误的层

计划层过度机械化：15-beat 被逐章硬映射，前四章分别是 Opening Image、Theme Stated、Setup、Catalyst；另有一条 chapter % 5 的节奏循环，把第 1、2 章固定判为 build_up，指导语直接写“本章以铺压为主”。起草层关键机制没到达：Scene-Sequel 的 Sequel 字段被 600 字大纲截断切掉，爽点、信息释放、节奏曲线根本没有进入 Writer Prompt。审查层只验事实：八个维度全是设定、时间线、连贯、角色、逻辑、节拍、伏笔、禁抄，明确“不评价文笔质量”“不建议情节改动”。

所以答案不是“过度”或“不足”二选一，而是分阶段两者都有：计划阶段过度约束，起草阶段使用不足，审查与修订阶段结构性缺位。

三、Stage 1 lite 的 3:0 是真实产物，但不能当作“文笔比较”

该 run 的硬测试里章回 0/12，四个两两维度全部 0–3 落败。但打开稿件会发现：章回写的是“陆衍 / 074 号沉河案 / 残痕视界系统”，而种子要求的是“林越 / 临汐城 / 白塔事故”。三本书共用同一份 immutable_seed，只有章回完全脱离了它。这不是文笔输，而是作者意图与种子设定的整体丢失。该 run 应作为“运行完整性缺陷”记录，不能用来证明 Jarvis 文笔更好。

证据：runs/pilot-tide-archive-001/stage1-benchmark-lite-001/ 的 final/stage1-benchmark-lite-summary.txt、reblind/private-map.json、hard-tests/BOOK-X9P/result.json 与三份 manuscript 的 immutable_seed。

四、“静止”是计划出来的，不是 Writer 临时写坏的

《重返巅峰》第 1 章的卷级节拍表把该章定为 Opening Image，并明确写“反派层级：无（仅环境/内心）”，目标是“做一个决定”，还禁止游戏战斗、禁止韩澈出场、禁止金手指。Writer 忠实执行了这个设计。《海港旧信》第 2 章同样如此：卷级节拍是 Theme Stated，正文是三段查资料，唯一的推进维度是“信息”。

规划不是没有约束，而是约束的方向错了：它约束“不要发生什么”，却没有约束“这一章必须让谁付出什么代价”。

五、审查与修订闭环结构上看不见文学问题

Reviewer 只查 8 个事实维度，所有 raw findings 强制 blocking=false；craft 类问题一律 ADVISORY，修订计划只收 PROSE_EDIT。第 2 章的 5 条发现里，0 阻断、0 高优，唯一像文学问题的“Sequel 决断拍缺失”被明确 deferred；实际进入修订的 4 条全是事实一致性。分数是“100 减去缺陷罚分”，文档自己写着“100 表示没有检测到缺陷，不是文学质量”。

于是系统可以在一个“近乎静止”的章节上给出 78 分，并报告“无阻断”。这不是审查器不努力，而是它的职责定义里根本没有“这一章好不好看”。

六、主责在规划层与度量层，不在 Writer

Writer 拿到的盲评文学分是三家里最高的，文字也确实是《海港旧信》里最扎实的部分。它的问题是被放进了一个“不许有对手、不许有代价、只许推进信息”的章节任务书里。把责任推给 Writer，会掩盖真正的机制问题：章节没有被要求成为一个戏剧单位。

02

现在如何写一章

从用户输入到正式正文。每一步都标了执行者、输入输出、生效的理论，以及“为什么当初这样设计”。

主链路在 skills/webnovel-write/SKILL.md。核心设计是“单一只读包”：Context Agent 产出一份创作任务书，Runtime 把它封进 WriterPackage，Writer 只允许读这一份渲染后的 Prompt，禁止再拼装或追加零散提示。这个设计解决了早期“多来源提示互相打架”的问题，也带来一个副作用：包里有什么，Writer 就只能看见什么；包里被截断的，Writer 永远看不见。

0

入口与前置检查

Skill / runtime

用户执行 /zhanghui:write。Step 0 检查项目状态、目标章、前章是否 accepted、运行时是否可写。

为什么：防止在未提交的前章上继续写，避免“正文在跑、账本没跟上”。

输入：章号 / 项目根输出：可写状态
1A

运行时合同与治理上下文

story-system

story-system --persist --emit-runtime-contracts → write-gate prewrite → runtime prepare → runtime governed-context。产出 Canon、Intent、Craft、Reader Signal、genre profile、writing guidance。

为什么：把“可写事实”和“创作意图”分开，先冻结事实，再让创作层引用。问题在于，这一层同时把节奏、题材、审查趋势等启发式也算了进来，而它们的质量参差不齐。

输出：governed_context.json输出：prewrite 校验
1B

Context Agent 写创作任务书

context-agent

消费 CANON / INTENT / CRAFT / REFERENCE，产出五段式 Creative Brief：本章要发生什么、人物怎么动、场景怎么走、信息怎么放、章末怎么收。

为什么：把“研究”与“写作”分离，让 Writer 不必自己翻档案，减少事实漂移。副作用是任务的“戏剧设计”也被前置固化：Brief 写得越细，Writer 越没有空间把一章变成一个真正的场景。

输出：creative_brief实际大小：9,983 B（ch1）→ 13,302 B（ch2）
1C

封包与渲染唯一的 Writer Prompt

runtime attach-creative-brief

把 Brief 封进 WriterPackage，调用 to_writer_prompt() 渲染六层：Story Identity、Current Intent、Governed Canon、Creative Brief、Constraints & Craft、Writer Context，末尾附 Handoff Protocol。

为什么：保证 Claude Skill Writer 与外部 Host Writer 看到逐字相同的输入，避免“同一个项目两种写法”。

输出：writer_prompt_000N.txt海港旧信 ch2：28,991 B
2A

Writer 起草

Writer

只读 writer_prompt_000N.txt，输出正文 + <chapter_changes> 结构化提案块。Skill 明确“禁止并步 / 跳步 / 自创模式”“严禁重新拼装 Writer Prompt”。

为什么：把创作收束为单次生成，减少多轮拼接带来的事实漂移。代价是：如果 Prompt 里的章节设计是静止的，Writer 只能把静止写得很好。

输出：draft 正文输出：chapter_changes
2B

文风适配、正文校验、语义判定

style adapter + judge

风格适配与 prose validate 之后，Semantic Judge 比较 before/after，输出 STYLE_ONLY_SAFE / SEMANTIC_CHANGE_PROPOSED / UNCERTAIN。

为什么：润色最容易悄悄改事实，语义判定是为了在“去 AI 味”与“别改设定”之间设一道闸。

观测：海港旧信 ch2 的 judge verdict 为 STYLE_ONLY_SAFE，changes=[]，Step 2B 实际近乎空操作；ch1 则出现整段编号与时间被改写、再由 Step 4 回退的情况。判定由 Writer 同模型的宿主执行，属于自审。

输出：candidate prose输出：judge verdict
3

Reviewer 事实审查

reviewer

只查 8 个维度：setting / timeline / continuity / character / logic / beat_compliance / foreshadow_compliance / do_not_copy_violation。所有 raw findings blocking=false；明确“不评价文笔质量”“不建议情节改动”。

为什么：早期 Reviewer 曾因“文笔不好”“这里该加反转”这类主观判断制造大量无法收敛的争论，2026-10-08 的 67bb4c2 把 craft / style 全部降为 advisory，Reviewer 被重新定义成“章节事实审查员”。这是自觉的设计选择，不是遗漏。

输出：review_results.json输出：dimension_results
4

修订计划与局部改写

revision planner

revise plan 按 owner 分流：只有 PROSE_EDIT 进入正文；ARTIFACT_REPAIR / GOVERNANCE_REPAIR 走账本；craft 类一律 ADVISORY，提示“仅记录建议”。自动修订预算最多 2 轮。

为什么：保护 Canon，避免为了“清零 advisory”反复改写正文。预算收缩的直接证据是 2026-10-21 第 4 章 Full Write：额外 2 轮花掉 730.9 s，占总墙钟 67%，而 gate 结果没有变化。

输出：revision_plan.json输出：revised prose
4.5

changes gate 与 anti-slop advisory

changes_gate

核对 chapter_changes 与正文是否一致；anti-slop 双引擎只做 advisory 扫描，不阻断。

为什么：状态变更必须可追溯；去 AI 味是风格问题，不应升级为事实阻断。

输出：changes 校验输出：anti-slop 报告
5

Data Agent、对账、ChapterCommit

data-agent

从最终正文提取事实，生成 commit artifacts，对账后提交。未落库 review_metrics 不得进入 Step 5。

为什么：正文是唯一事实源，账本必须从正文反推，而不是从计划复制。

输出：commit输出：index / projection
5.5

发布与备份

publish + backup

正式发布门禁通过后写入 accepted 正文，生成备份。

输出：accepted 章节输出：backup

Writer 真正看到了什么

以《海港旧信》第 2 章的 writer_prompt_0002.txt 为例，28,991 字节的构成如下。创作任务书接近一半，交付协议与上下文线索合计超过四分之一，真正的事实与意图只占不到两成。

本章写作意图 8.9% 治理事实 9.9% 创作任务书 45.9% 约束与工艺 7.2% 前情线索 17.8% 正文交付协议 10.0%

字节数由本轮只读统计得出，按 Prompt 的六个一级标题切分。占比不等于注意力占比，但它决定了 Writer 必须先读完什么。

层本应提供实际缺陷后果
Current Intent核心目标、阻力、代价、钩子、必须节点大纲被截断为前 600 字，sequel_dilemma / sequel_decision 永远落在截断之外。Scene-Sequel 只剩 Scene；人物在场景结束后没有“消化与决断”。
Governed Canon登场角色、当前状态、已确认事实appearing_characters 只有 entity_id，渲染代码找不到 name / id，于是输出 8 行“- 角色”；canon_items 的 content 是字典，直接以 Python repr 打印。Writer 拿到的是“角色”占位符和 {'entity_id': 'xu_zhiyuan', ...}，不是可用的人物状态。
Constraints & Craft题材指引、节奏策略、工艺建议项目正典题材是“悬疑”，但 primary_genre 写的是“规则动物园”，解析成了 rules-mystery（规则怪谈）；chapter % 5 把第 2 章判成 build_up，指导语为“本章以铺压为主”。一本现实向悬疑，被塞进了规则怪谈的“规则先于解释、代价先于胜利”和“先铺压”的创作策略。
Writer Context前情摘要、紧急伏笔、参考依据直接 dump story_craft.foreshadow_chain.N.* 路径；33 条参考项只渲染 3 条。上下文占比不小，但可读的有效信息密度低。
Handoff Protocol8 字段 CHANGES 协议、枚举、R3 规则约 2.9 KB，占 10%，包含大量“不要写什么”的格式约束。写作注意力被格式合规分走；这是为账本服务的，不是为小说服务的。
设计意图不等于执行效果。“单一只读包”在工程上是对的：它消除了多来源冲突，让每次生成可复现。但它同时把“计划的质量”放大成了“正文的上限”。当计划把一章定义成“无对手的铺垫”，Writer 的忠实反而成了缺点。
03

理论从哪来，后来变成了什么

不是通用写作理论清单，而是这个仓库真实发生过的导入、强制、降级与失修。

时间提交 / 文档发生了什么对文学机制的影响
2026-08-14a085978新增 story-craft-engine 设计稿：Tier 1 八机制、Tier 2/3 备选、Tier 4 明确拒绝。理论被一次性大量导入，但设计稿本身已区分“v1 必做 / v2 以后 / 只做参考”。

2026-08-1479d534c新增 8 篇 references/shared/ 参考文档。理论从“文档”进入“可被 Skill 引用的规则库”。
2026-08-148ad588aPlan Step 4.5：强制生成 15-beat 卷级节拍表。Save the Cat 从参考变成硬规划步骤；卷级结构开始决定章级任务。
2026-08-147ba848dPlan Step 7：Scene-Sequel + beat 字段变为必填。Dwight Swain 进入章纲；但校验只查字段存在，不查 Sequel 是否真的写进正文。
2026-08-145ca569a / 1541a06Reviewer 集成 story_craft 检查，扩展到 7 维。节拍与伏笔开始被审查，但审查对象是“合规”，不是“好看”。
2026-10-0867bb4c2“keep craft and style findings advisory”：craft / beat / foreshadow / rhythm / hook / style / anti-slop 全部降为 advisory；review_schema 强制 blocking=false。关键转折。文学相关发现从此不能阻断、不能进入正文修订。系统正式变成“事实审查器 + 风格扫描器”。
2026-10-2030d6539 / 362e9cf两轮审计修复，继续修补 advisory 链路。没有恢复文学判断，只让 advisory 更稳定。
2026-10-21Full Write ch4 证据额外 2 轮修订 730.9 s，占 1090 s 的 67%，gate 未变；随后把自动修订预算压到 2 轮。系统自己承认“多轮审改不等于更好”，但只修了预算，没有改审改的对象。

这条时间线解释了一个表面矛盾：为什么导入了这么多理论，正文却越来越“稳而平”。因为理论在 8 月被强制进计划，在 10 月又被主动降级出修订。它只保留了“计划时约束你”，取消了“写完后判断你”。计划层越来越硬，反馈层越来越软，最后只剩下事实一致性是硬的。

判定口径：EFFECTIVE = 有可指认的执行与效果；PARTIAL = 部分到达、部分失效；INEFFECTIVE = 到达了但没产生目标效果；NOT_REACHED = 有实现但运行时没被喂数据/没进入 Writer；NOT_IMPLEMENTED = 只在文档或设计稿；CONFLICTING = 与另一条生效规则互相抵消；COUNTERPRODUCTIVE = 产生反向噪音；UNDETERMINED = 证据不足。

盘点结果

22 条被点名的机制里：1 条在窄指标上有效（去 AI 味 detector），2 条部分到达（伏笔、钩子），2 条到达但无效（Scene-Sequel、Goal/Conflict/Disaster），3 条有实现但运行时没被喂数据（节奏曲线、爽点、Strand Weave），9 条只在文档或设计稿，2 条互相冲突（15-beat 与章高光、题材路由），1 条反向制造噪音（限时锁），2 条证据不足（人物弧光、主题回声）。

这不是“理论越多越好”或“理论越多越差”的证明。它证明的是：理论被导入后，没有被分成“计划工具 / 起草工具 / 评估工具”三层，而是被混成了一层硬约束。

5.2 《海港旧信》第 2 章：三段查资料，为什么审查说“没问题”

第 2 章 2,120 个汉字，87 段，31 段含对话（36%），两个 --- 场景切换，三个地点：档案科、地方志/旧报库、旧潮位站。表面上看，它比第 1 章“动”得多。但三段的功能完全同构：去一个地方，查一份材料，抄下一个证据，离开。

  • 场景 1（档案科）：找目录卡片，发现“限制查阅”，在申请单前停住，没有递进去。阻力是制度，不是人。
  • 场景 2（地方志 + 旧报库）：查到一行事故记载，核对日期，抄下书名、版次、页码。收益是“日期对上了”。
  • 场景 3（旧潮位站）：补核清单，遇到梁沐，问了两句设备，听到“那批设备是事故之后统一换的”。章末没有反应与决断，只有“螺丝刀转半圈，停一下，再转半圈”。

这一章的推进义务在 Writer Prompt 里是这样写的：“行动推进、信息推进、关系推进、状态推进、位置推进或资源推进之一”。“信息推进”单独就可以过关。章节计划也确实是这么设计的：卷级节拍第 2 章是 Theme Stated，不是 Catalyst。于是 Writer 忠实地写了一个“主题被点出、但主角没有付出代价”的章节。

关键机制：Reviewer 的职责定义里没有“这一章是否好看”。它只能报“Sequel 字段没在正文显化”，而这条又被降为 advisory，不能进修订。于是系统同时完成了两件事：正确地识别了文学问题，又正确地拒绝处理它。

5.3 修订到底改了什么

第 2 章的 revision_plan_0002.json 有 4 个 target，全部是 LOCAL_FACT / PROSE_EDIT：

  • 梁沐的“那边早停用了，不派工单”与他在本站作业的事实冲突，改为“拆之前最后一轮。别的早停了。”
  • 目录卡片缺少日期/编号证据链，补入“卷宗编号里带着 0317”。
  • 第十项“补核”缺少正文证据，补一句“把小圈划掉，在旁边打了一个勾”。
  • “入职那年有人跟他说过一句话”指代不明，改为“科里一个老人跟他说过一句，不要问三月那件事”。

这些修改都是真实的、必要的，文本也更准确。但它们全部是事实一致性修复，没有一条让章节多一个对手、多一个代价、多一次选择。Semantic Judge 的 verdict 是 STYLE_ONLY_SAFE，changes=[]，说明这次修订在语义层几乎没有动作。对比第 1 章，Step 2B 曾把编号 1→7…13→19、时间 09:15/12:15 改写成 11:40，随后 Step 4 又回退大半。**修订链路是“事实修补器”，不是“文学编辑器”。**

5.5 Jarvis 具体赢在哪，不赢在哪

观测 在 Stage 3 的三章里，Jarvis 的阅读吸引力均值 3.833，章回 2.750；但 Jarvis 的文学质量 4.167，低于章回的 4.333。它不是“文笔更好”，而是“更像一章会发生事情的小说”。可指认的差异集中在五处：

  • 事件密度：Jarvis 第 1 章在 1,598 字里完成了接单、忍痛、开播、同行对峙、旧怨暴露、隐藏规则预告；章回在 2,213 字里完成了看网页、回忆、决定登录。
  • 人物 agency：Jarvis 的主角在章内做了多个有代价的选择；章回的主角主要是观察与犹豫。
  • 当页冲突：Jarvis 有韩澈与直播间的即时反馈；章回的冲突是“行业不景气”“手会老”这类背景压力。
  • 对话：Jarvis 32% 的段落含对话，且对话承担信息与冲突；章回 12%，且多为心理自问。
  • 章末拉力：Jarvis 用倒计时与未解释的旧怨挂起两个问题；章回用“决定登录”挂起一个读者还不在乎的问题。

推断 这些差异与两套系统的章节设计一致：章回的卷级节拍要求第 1 章做 Opening Image，且明确禁止冲突；Jarvis 没有同等的“第 1 章不许有对手”的约束。**但 Jarvis 内部如何做到这一点，本轮没有审计其源码，不能断言其因果机制。** 中置信

不要把 Stage 1 lite 当作反例。该 run 的 0–3 是真实的，但章回稿件写成了另一本书。它证明的是“种子遵循/运行完整性”会灾难性失败，不证明“Jarvis 文笔更好”。Stage 2 的 1/30 同理，是 HALT，不是文学比较。
06

根因排序

按“对可读性的实际影响”排序，最多五条。每条都给出机制、真实产物证据、与 Jarvis 的差距、置信度、建议与最小验证。

CAUSE 01

章节没有被要求成为一个戏剧单位

现象
第 1 章可以整章停在登录之前；第 2 章可以是三段查资料；章末可以只有一个钩子台词，没有反应与决断。
机制
15-beat 把前四章定义为 Opening Image / Theme Stated / Setup / Catalyst；progress_obligation 允许“信息推进”单独过关；Scene-Sequel 的 Sequel 字段在 Writer Prompt 里被截断。
证据
《重返巅峰》ch1 节拍表“反派层级：无（仅环境/内心）”；《海港旧信》ch2 三段查资料；Writer Prompt 600 字截断（chapter_runtime.py:292）。
差距
Jarvis ch1 在 1,598 字里完成接单、冲突、开播、旧怨、倒计时；章回在 2,213 字里完成观察与决定。
置信度
高 计划文本与正文一一对应，不是事后解释。
建议
保留 15-beat 作为卷级诊断，删除“信息推进即可”的单独豁免；把“非声明过渡章必须有 1 个当页对手 + 1 个不可逆代价/选择”设为唯一下一阶段硬约束。
最小验证
同一章纲、同一 Writer，只改这一条约束，做 2 臂单章 A/B，盲评阅读吸引力；不重跑三章 Benchmark。
CAUSE 02

审查与修订闭环对文学质量结构性失明

现象
一个“近乎静止”的章节得到 78 分、0 阻断；唯一像文学问题的 Sequel 缺失被 deferred；修订只改事实。
机制
Reviewer 只查 8 个事实维度，明确“不评价文笔质量”“不建议情节改动”；所有 findings blocking=false；craft 一律 ADVISORY；revision_planner 只把 PROSE_EDIT 放进正文。
证据
agents/reviewer.md:17,187–188；review_results.json 5 条 0 阻断；revision_plan_0002.json 4 条全 PROSE_EDIT、2 条 deferred。
差距
Jarvis 没有同等的“只验事实”闭环；它的开篇可以承担冲突与人物交锋。章回的闭环会主动把这类问题降级。
置信度
高 职责文本与产物一致。
建议
不要再把 Reviewer 分数当文学质量；要么明确它只是事实检查器，要么另设一个不参与 gate 的“文学读稿”步骤。不要给现有 Reviewer 加维度。
最小验证
用现有 3 章做相关性检查：审查分 vs 盲评阅读吸引力。若相关性接近 0，就确认分数不能作为质量代理；无需新运行。
CAUSE 03

质量反馈信号为空或反向，并回流到下一章 Prompt

现象
第一章的写作指导写着“最近审查均分 0.0 低于阈值 75.0，建议先保稳：减少跳场、每段补动作结果闭环”；Context Agent 又把“90 分 / 其余满分”读成“不需要更用力”。
机制
overall_avg = float(review_trend.get("overall_avg") or 0.0)；没有审查数据时返回 0.0，触发“低分保稳”分支。未评维度初始 100.0，只对报出的问题扣分。
证据
writing_guidance_builder.py:104–127；review_schema.py:201–204,250；《重返巅峰》ch1 Writer Prompt 的“先保稳”；《海港旧信》ch1 指导中的“90 分/其余满分”。
差距
Jarvis 的开篇没有“先保稳”的内部指令；章回在第一章就被告知“最近表现很差”，于是选择更保守的写法。
置信度
高 代码分支与 Prompt 文本可直接对应；“保守导致静止”是 推断 中。
建议
无数据 = 无信号，不要当 0 分；未评维度不要默认 100；不要再把缺陷罚分写进创作任务书作为“质量趋势”。
最小验证
同一章、同一模型，去掉“先保稳”一行，比较场景跳转数与章末决断拍；n=1 诊断即可。
CAUSE 04

理论被过度机械化，启发式覆盖了故事

现象
第 2 章被固定判为 build_up，指导语“本章以铺压为主”；一本现实向悬疑被告知“按规则怪谈叙事主线推进”“规则先于解释，代价先于胜利”。
机制
stage_mod = chapter % 5；primary_genre="规则动物园" 被解析成 rules-mystery，覆盖了 canonical_genre="悬疑"；15-beat 被逐章映射成任务。
证据
writing_guidance_builder.py:121–127；.story-system/MASTER_SETTING.json 的 route.primary_genre 与 canonical_genre；governed_context_0002.json 的 guidance 文本。
差距
Jarvis 没有“章号取模决定节奏”的规则；它的章节节奏由当前事件决定，而不是由章号决定。
置信度
高 代码与配置直接可见。
建议
删除 chapter % 5；题材解析以 canonical_genre 优先，并为“悬疑”补上 mystery 别名（当前 to_profile_key("悬疑") 返回“悬疑”，不是有效键）；15-beat 只做卷级诊断，不做章级任务分配。
最小验证
用同一章纲，分别用“规则怪谈”和“悬疑”两套 guidance 生成 brief，人工比较哪一套更贴近本书；n=1。
CAUSE 05

Writer 实际收到的包被截断、占位与稀释

现象
大纲只保留前 600 字，Sequel 字段永远看不到；登场角色渲染成 8 行“- 角色”；Canon 事实以 Python dict repr 出现；交付协议占 10% 的 Prompt。
机制
outline[:600]；c.get("name") or c.get("id") or "角色"，而数据里只有 entity_id；content 是 dict 却直接 f-string。
证据
chapter_runtime.py:292,303,313,326；writer_prompt_0002.txt 的实际渲染。
差距
Jarvis 的 Writer 不被要求同时解析 2.9 KB 的账本协议；章回的 Writer 要在格式合规与场景写作之间分注意力。
置信度
高 渲染缺陷可直接复现；“稀释注意力导致文学损失”是 推断 中。
建议
修复渲染：不截断大纲，entity_id 映射为角色名，Canon 输出“实体 / 字段 / 值”的可读文本，Handoff 协议移到独立文件或按需加载。
最小验证
同一章、同一模型，用完整大纲 + 可读 Canon 重跑一次 Writer，检查 Sequel 决断拍是否出现；n=1 诊断。

责任分配

规划层（Planner + Context Agent）主责：它决定了这一章有没有对手、有没有代价、有没有决断。度量闭环（Reviewer + Revision Planner）次责：它不仅看不见文学问题，还把“缺陷少”包装成“质量高”。Writer 不是主责：它的盲评文学分是三家里最高的，文字本身是产物里最强的部分。修订不是主责：它被设计成事实修补器，不能要求它做它没有权限做的事。

07

最小改进路线

不实施，只冻结方向。三条决策 + 一个可选修复，按优先级排列；每条都给出可验证的最小实验。

把“章节戏剧义务”设为唯一下一阶段硬约束

非声明为过渡的章节，必须包含：一个当页可指认的对手（人物、制度的具体执行者、或环境的直接反噬），一个不可逆的代价或选择，以及章末人物对结果的反应与决断。声明为过渡的章节必须显式标注，且每卷不超过一章。

取消“信息推进”单独满足 progress_obligation 的资格。信息可以推进，但只能作为行动或关系变化的结果，不能作为唯一变化。

为什么是这一条：它同时修掉 Cause 01 和 Cause 05 的一半；不需要新理论，只是把已有的 Goal/Conflict/Disaster 与 Scene-Sequel 真正执行到章级。最小验证：同一章纲、同一 Writer，2 臂单章 A/B，盲评阅读吸引力与“章末是否想翻页”；不重跑三章 Benchmark。

把审查分从“质量信号”降级为“事实缺陷计数”

无审查数据时返回“无信号”，不要用 0.0 触发“先保稳”；未评维度不要默认 100；不再把“90 分 / 其余满分”写进 Creative Brief 作为“不需要更用力”的依据。Reviewer 继续只做事实审查，但它的分数不再进入创作指导。

为什么是这一条：Cause 03 是当前最便宜、最确定能修的反向信号。它不改变审查职责，只切断错误回流。最小验证：用现有 3 章做“审查分 vs 盲评阅读吸引力”的相关性检查；若相关性接近 0，确认分数不能当质量代理。无需新运行。

理论分层：卷级诊断、章级执行、评估分离

15-beat 只用于卷级诊断，不逐章分配任务；删除 chapter % 5 的节奏循环；题材解析以 canonical_genre 优先，并为“悬疑”补上 mystery 别名；停用没有运行时调用者的 rhythm_curve / pacing_history / expectation_debt 计数器，或明确标注“未接线”。

为什么是这一条：Cause 04 的错配不是“理论不好”，是“理论被放在了错误的层”。减法比加法更能恢复故事的空间。最小验证：同一章纲，分别用当前 guidance 与“去掉取模、canonical genre”的 guidance 生成 brief，人工比较哪一套更像这本书；n=1。

可选但低成本：修 Writer 包的渲染

大纲不截断；entity_id 映射为角色名；Canon 输出“实体 / 字段 / 值”；交付协议独立或按需加载。它不改变创作理论，只让已有的 Scene-Sequel 真正到达 Writer。

为什么放在最后：它是明确的工程缺陷，但单独修它不足以让章节“有对手”；它应该与决策 1 一起验证。最小验证：同一章、同一模型，完整大纲 + 可读 Canon 重跑一次，检查 Sequel 决断拍是否出现；n=1。

明确不做什么

  • 不新增写作理论、不新增 Reviewer 维度、不新增质量检查器。
  • 不把“增加 Prompt 长度”当默认解决方案；本轮的所有决策都不增加 Prompt 总长度。
  • 不重跑三章 Benchmark、不重跑 Full Write；所有实验都是单章、2 臂、可回退的诊断。
  • 不修改 Data Agent、vector projection、ChapterCommit；它们不是本轮根因。
  • 不把 Stage 1 lite 的 0–3 当作文笔结论；它是运行完整性缺陷，需单独修。
一个需要单独记录的风险。Stage 1 lite 中章回稿件完全脱离种子（陆衍 / 074 / 残痕视界），而同一 run 的另两本书都遵循了种子。这不是文学问题，是“生成前 seed 是否真的进入 Writer”的运行完整性问题。它可能来自错误的项目绑定、初始化失败或上下文丢失；本轮没有足够证据定位到具体代码路径。**在修文学机制之前，必须先确认这条链路不会再次发生**，否则任何文学实验都可能测到另一本书。
08

收口七问

用最短的答案回答本轮必须回答的七个问题。展开证据在前文。

Q1

章回现在到底怎么“写”一章？

Runtime 先冻结事实与意图，Context Agent 写一份接近一半 Prompt 体量的创作任务书，Runtime 把它封成唯一的 Writer Prompt；Writer 一次性写出正文与账本提案；Reviewer 只查 8 个事实维度；Revision 只修事实；Data Agent 从正文反推账本；提交、发布、备份。整条链路的核心是“单一只读包 + 事实闭环”，不是“场景写作”。

Q2

导入的理论，真正被用上的有多少？

22 条被点名的机制里，1 条在窄指标上有效，2 条部分到达，2 条到达但无效，3 条有实现但运行时没被喂数据，9 条只在文档或设计稿，2 条互相冲突，1 条反向制造噪音，2 条证据不足。真正进入 Writer 并且改变正文的，主要是 15-beat 的卷级骨架、角色弧光的静态描述、部分伏笔回收与钩子字段。

Q3

哪些理论有效，哪些无效？

有效但窄：anti-slop 对可计算的 AI 味指标。部分有效：伏笔链、6 种钩子，但只到达“字段”层面。无效：Scene-Sequel 的 Sequel 被截断；Goal/Conflict/Disaster 被“信息推进”豁免。没到达：节奏曲线、爽点、Strand Weave。冲突：15-beat 的前四章铺陈 vs 章级高光；规则怪谈 guidance vs 现实悬疑。反向：限时锁在审查时读到旧状态，重复报逾期。

Q4

是否存在理论冲突或约束过载？

有，而且不止一处。最硬的一处是“卷级 15-beat 要求第 1 章做 Opening Image、前四章做 Setup”与“章级规划文档要求每章都有高潮”直接冲突；实现选择了前者。第二处是“现实向悬疑”的正典题材与“规则怪谈”的题材 profile 冲突，后者来自 primary_genre 的路由覆盖。第三处是“先保稳、减少跳场”的反馈信号与“追读需要变化”的目标冲突。第四处是 2.9 KB 的账本协议与 13 KB 的创作任务书争夺同一份注意力。

Q5

文学差距的主责在 Writer、Planner、Reviewer 还是 Revision？

主责在 Planner + Context Agent：它们把章节设计成“无对手的铺垫”和“信息推进”。次责在 Reviewer + Revision：它们结构上看不见文学问题，还把“缺陷少”输出成“质量高”。Writer 不是主责：它的盲评文学分是三家里最高的，文字是产物里最强的部分。Revision 也不是主责：它被权限设计成只能修事实。

Q6

为什么章回赢一致性，却输文学表达 / 读者偏好？

先修正前提：在 Stage 3 的三章盲评里，章回并没有输文学表达，它输的是阅读吸引力。原因是系统只把“一致性”做成了硬目标：Canon、Intent、Reviewer、Revision 全部围绕事实闭环；而“这一章有没有对手、有没有代价、有没有让读者想翻页”没有任何硬约束，甚至在计划层被明确禁止。Writer 被放进一个“不许发生事情”的任务书里，忠实执行，于是文字越干净，章节越静止。Jarvis 的优势不在更华丽的句子，而在章内事件密度、人物 agency、当页冲突与章末拉力；这些是章回的计划层主动放弃的。

Q7

下一步最该改的一个机制是什么？

章节戏剧义务。不是新理论，而是把已经导入的 Goal/Conflict/Disaster 与 Scene-Sequel 真正执行到章级：非声明过渡章必须有 1 个当页对手、1 个不可逆代价/选择、章末反应与决断；取消“信息推进”单独过关。它一条就能同时修掉“静止的章节”“被截断的 Sequel”“审查看不见文学问题”三个症状的交汇点。先做单章 2 臂诊断，不重跑 Benchmark，不进入实施。
