## 1. 压力清单是怎么自动生成的

不是人工整理的摘要。`build_pressures_from_state` 只读 `state.json` 的五个既有来源：

| 来源 | 派生成什么 | ID |
|---|---|---|
| `story_craft.timed_locks` | 有截止章的卷级承诺 | `TL-###` |
| `story_craft.foreshadow_chain` | 已埋、未回收的伏笔 | `FS-###` |
| `plot_threads.foreshadowing` | 未回收的 open loop | `LO-<loop_id>` |
| `entity_state.<id>.stance / decision / belief / warning_status / procedure_compliance` | 角色承诺、未决决定、风险 | `CH-<entity>-<field>[-<key>]` |
| `chapter_meta.<prev>.sequel_decision` | 上一章交给本章的后果 | `PREV-<n>` |

三条筛选规则（都是确定性的，不看语义）：

1. **未来埋的不算**：`buried_chapter > chapter` 的伏笔/open loop 不进清单。
2. **已回收的不算**：`status` 落在 resolved/paid/fulfilled/closed/回收 等集合里的排除。
3. **记录过期的不算债**：截止章已经落在 accepted 正文里的锁，标 `stale`，沉到最底并标注
   「记录未更新」——它是台账没跟上，不是规划者要还的债。这一点必须区分，否则第 6 章内
   就该兑现的合作关系会被渲染成「已逾期 1 章」，让规划者以为承诺没兑现。

排序：临近到期（≤3 章）→ 角色承诺（`stance` 优先）→ 上一章后果 → 有截止章的锁/伏笔 → 其余。
每个 kind 有配额（`previous_consequence` 1 / `deadline` 2 / `character` 4 / `foreshadow` 2 /
`open_loop` 1），防止一个字段很多的角色占满全部名额。默认 8 条，条目文本截断到 140 字。

第 7 章实跑输出 884 字：

```
- **FS-006 · 剩 2 章**（foreshadow）旧潮位站值班记录本上多出一行十年前的笔迹
- **CH-xu_zhiyuan-stance-anonymous_letter**（character）未上报；决定先自行核实
- **CH-xu_zhiyuan-stance-liang_mu**（character）许知远承诺不写梁沐的名字…
- **CH-xu_zhiyuan-stance-zheng_pei**（character）确认郑培知情程度超出职位应有范围…
- **CH-xu_zhiyuan-warning_status**（character）科长电话警告：海事的事别掺和…
- **PREV-6**（previous_consequence）梁沐说"那天潮位站该在检修期" → 下章目标
- **TL-001 · 剩 5 章**（deadline）Midpoint 必须发生
- **TL-002 · 剩 11 章**（deadline）All Is Lost 必须到达
（另有 33 条较低优先级压力未列出）
```

清单**不进 Writer**：`render_chapter_structure` 不渲染 `story_pressures`，`extract_outline_residual_notes`
也已把它当作已识别字段吞掉。它只服务规划与 `plan-check`。

## 3. 声明是否真的可核查

两臂都只引用了清单里真实存在的 ID，且**各自选了不同组合**（a 用 `PREV-6`，b 用
`CH-xu_zhiyuan-stance-liang_mu`），说明清单是被判断后使用的，不是被照抄。

`plan-check` 对同一份 24 章大纲的输出从

```
ok=True policy_action=ALLOW          # 改动前：这份把活压力全排除的大纲完全合格
```

变成

```
ADVISORY [story_structure_repeated] 第7、9、12章在 6 章内重复使用同一种章节结构（solo：许知远）
```

即：**它现在能指出第 7 章是同一场戏的第三次**。这是本轮唯一新增的、针对真实数据的具体发现。

同时确认没有制造假门禁：未使用该约定的旧卷（本卷 24 章全部未声明）**不会**逐章刷屏，
只在真正出现「6 章内 3 次同结构」时报一条。

## 4. 结构重复检测为什么用「同形 + 同组角色」

试过三种信号，只有一种同时通过「抓住真问题」与「不误报」：

| 信号 | 第 7 章 | 第 15–18 章 | 结论 |
|---|---|---|---|
| 连续同形（solo/multi） | 命中 | **误报**（4 章连报） | 否 |
| 节点文本相似度（4-gram） | **漏报**（第 5 与第 7 章共享 0 个 4-gram） | 不误报 | 否 |
| 同形 + 同组出场角色，6 章内 ≥3 次 | 命中 7/9/12 | 不误报（4 章 4 组不同角色） | **采用** |

## 5. Canon 审查（对抗式，n=1 臂先做）

对 `After-a` 做了一次独立的对抗式 Canon 审查（不看其它臂，只看 Canon 与这一份章纲）。
结论：**不通过**，一处严重越界。

> 老周把窗台上的铁盒（六月巡检表）放进纸箱交给档案科。

Canon §5 明确写老周「拒绝交出站内任何纸质材料」，第 3 章他说「站里的纸不能外拿」，
而铁盒在 Canon 里是「在老周铁盒里」的未建立物。`After-a` 让他在清单外主动交出来，
既推翻了既定事实，也违反该臂自设的禁区「老周的配合只能来自清单」。

另有 2 处中等、3 处轻微问题（新造「港务拆站项目组」这一机构权限；「实收十一项，缺二项」
把移交清单与 10/9 的十三项资产清点单混为一谈，而值班记录本 Canon 明写「不在本次清点范围内」；
「第一次把名字写进这件事」与第 3–4 章已留痕冲突；「三天前」应为四天；「站里那批月报」
地点错，立卷的合订本在档案科后楼库房）。

**这三处都不是压力清单导致的。** 逐臂核对：

| 臂 | 铁盒 | 六月巡检表 | 明确守住「不外拿」 |
|---|---|---|---|
| `After-a` | 交出 | 随箱入库 | ✗ |
| `After-b` | **仍然不开** | 未涉及 | ✓ |
| `After-c` | 未涉及 | 未涉及 | ✓ |

`After-b` 甚至把「老周只交记录本、不开铁盒」写成了新埋的伏笔，并明确写
「十年不交站内任何一张纸，平房里的铁盒不开」——它对同一条 Canon 的遵守比 Before 更严。
所以越界是**单次采样的判断失误**，不是这条桥的机制性后果。

**这一点必须如实记入结论**：3 次采样里有 1 次越界。压力清单提高了「承接已有故事」的概率，
但它不保证 Canon 安全；Canon 安全仍然依赖 Reviewer 与人工判断。

## 6. 收口

**PRIMARY QUESTION 的答案：是（带一个明确的保留）。**

- 压力清单来自真实 `state.json`，不是实验者整理的摘要（这是上一轮 C 判负的混杂因素，本轮消除）；
- 规划者在章纲里显式声明承接了哪几条，机器可对照同一份派生结果验证，且注解/暂缓语法不会产生假 ID；
- 3 次采样的第 7 章都明显更承接已有故事，结构都避开了 Before 的重复；
- **但 3 次里有 1 次 Canon 越界**（老周交出铁盒）。这条桥不替代 Canon 审查。
- 未新增 Agent、未新增 Schema、未新增数据库、未改动 Writer / Finalizer / Reviewer / Skill Router。

保留实现，提交 PR；越界风险写进报告与 study 文档，不隐藏。

## 7. 局限

- 每臂 n=3，只能说明方向，不足以估计模型方差。三次采样在「结构形状」上完全一致（都是
  `multi`，即不是 Before 那种单人闭环），但在具体入口与落点上分歧明显——这说明清单约束的是
  「这一章必须接住哪条债」，不约束「用什么方式接」，符合设计意图。
- Before 是既有生产章纲，After 是重新规划；两者的输入不完全对等（After 多了一份清单，
  也多了 `prompts-After.md` 里的五条规划要求）。**因此本轮不能把提升单独归因于清单本身**，
  只能说「清单 + 显式声明 + 五条要求」这一整条链有效。要拆开归因需要再加一个「同五条要求、
  无清单」的对照臂——本轮未做，因为 goal 要求的是判断这条桥是否值得上生产，不是做消融。
- 没有写正文。章纲更好不等于正文更好。

## 8. 实现过程中被真实数据与对抗式审查暴露的缺陷（均已修）

| 缺陷 | 怎么发现的 | 修法 |
|---|---|---|
| 逾期未更新的锁被渲染成「已逾期 1 章」 | 第 7 章清单里 `TL-005`（第 6 章内建立合作关系）截止章已 accepted，状态仍 `active` | 标 `stale`，沉底并改标「记录未更新（截止章已 accepted，不可再规划）」 |
| 结构重复在真实卷上刷屏 15 条 | 对 24 章大纲实跑 `plan-check` | 改为「同形 + 同组出场角色，6 章内 ≥3 次」，且只锚定尚未 accepted 的章 |
| 一次结构重复被报成 4 条 | 同一段 15–18 章连续 4 章 multi | 每个 signature 只报一次，列出该模式的全部章节 |
| 畸形 `state.json` 让 `plan-check` 崩溃 | 用 `{"plot_threads": "nope"}` 等 11 种畸形输入探测 | 全部派生路径改用容错取值；补 11 个参数化测试 |
| 两条记录派生同一 id 时静默丢条目 | 追加一条重复 `TL-001` 的锁 | 按 id 去重，保留排序更高的一条 |
| `；` 切 CPN 时把散文当成角色名 | After 臂的 CPN 含 `；`，签名里出现 `铁门漆上的号比 009 小` | 角色段超过 12 字或含句读 → 判为节点格式不合法，返回空 |
| **文档里写的暂缓语法根本无法解析** | 对抗式审查实跑 `无（本章为过渡，暂缓：FS-006）`，被 `，` 切成两个垃圾 ID，报假 unknown | `story_pressures` 改为保留原文；检查器用专用解析器只提取 `TL-/FS-/PREV-/LO-/CH-` 形状的 ID，并识别「暂缓」 |
| 零填充 `chapter_meta` 键（`"0006"`）查不到上一章后果 | 项目 `state_manager` 就写零填充键 | 改用项目自带的 `state_validator.get_chapter_meta_entry` |
| 去重发生在排序之前，最紧急的重复记录被丢掉 | 两条同 id 的锁，先收集到的是「很久以后」 | 排序后再去重 |
| open loop 的 `target_chapter` 从未读取，全部算无期限 | 最该还的 loop 可能被配额挤掉 | 用 `FORESHADOWING_TARGET_KEYS` 读取期限并参与排序 |
| 状态词表与项目 canonical 不一致（`已解决`/`完成`/`complete` 被当成活的） | 项目 `state_validator` 认这些写法 | 直接复用 `is_resolved_foreshadowing_status` |
| 已 accepted 的章也被要求补「承接压力」 | 冻结正文改不了，属于永久噪声 | 与结构重复检查一致：只锚定尚未 accepted 的章 |
| 非 UTF-8 的 `state.json` 让 `plan-check` 抛 `UnicodeDecodeError` | GBK/UTF-16 编码探测 | 捕获 `ValueError`，降级为空清单 |
| 由用户数据拼出的 id 无长度上限 | `LO-<loop_id>` / `CH-<entity>-…` 直接插值 | 加 `_clip_id`（60 字） |
