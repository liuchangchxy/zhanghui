## 第一性原理 7 公理回顾

| 公理 | 含义 |
|---|---|
| **A1 正确性** | 合法变更必须通过；非法变更必须被拦 |
| **A2 健壮性** | 任何输入都不能让系统崩溃；失败必须优雅 |
| **A3 终止性** | 任何输入必须在有限时间内完成 |
| **A4 确定性** | 同样的输入一定有同样的输出 |
| **A5 可组合性** | 多个规则同时运行不互相干扰；并集等于组合 |
| **A6 透明性** | 失败信息清晰、可操作、可定位；不误导、不模糊、不泄露内部 |
| **A7 安全性** | 输入不导致注入 / 穿越 / 资源耗尽 / 敏感信息泄露 |

## 公理 A1：正确性（新增）

### A1.1 — `[CRITICAL]` UTF-16 / GBK / Latin-1 等非 UTF-8 编码 → 系统崩溃

- **公理违反**: A1 + A2 + A6（输入决定输出，输入合法但系统崩 = 不可用）
- **来源代码**: `chapter_path.read_text(encoding="utf-8")` 在 `main()` 中
- **推导**: A2 要求"任何输入都不能让系统崩溃" → 任何字节序列（含 GBK、UTF-16 LE/BE、UTF-32、Latin-1）到达文件系统都必须被处理
- **测试**:
  - UTF-16 LE BOM 编码章节 → Python `UnicodeDecodeError` → 系统以 `rc=1` 退出，stderr 暴露 Python traceback
  - GBK 编码章节 → 同样崩溃
  - 截断的多字节 UTF-8 序列 → 同样崩溃
- **实际**: `Traceback ... UnicodeDecodeError: 'utf-8' codec can't decode byte 0xff`
- **严重度**: **CRITICAL**（LLM 输出章节后被任何工具转换编码 → 整个门禁不可用；用户看到 traceback 不知如何修复）
- **修复建议**: 与 `text_humanizer.py` 的 `_load_chapter` 函数一致，用 `try/except UnicodeDecodeError` 捕获并报 R0 错误。

### A1.2 — `[INFO]` 重要性大小写敏感性

- 实际: `"IMPORTANT"` → R2 失败；`"important"` → 通过。设计预期，prev review 已记录。

### A1.3 — `[INFO]` 边界值（30, -30, 30.0001, 31）— 全部正确

- 全部符合预期。

### A1.4 — `[INFO]` 枚举值"important" 的尾部空格 / 末尾换行 → 正确报错

- 实际: 报 `character_state_changes[0].importance='important ' 非法` ✓

### A1.5 — `[MAJOR]` Unicode confusables 静默通过

- 假设: character_id = Cyrillic 'а' (U+0430) 而账本是 Latin 'a' (U+0061) — R3 正确拒绝。
- 假设: `elapsed_time = '１年前'` (全角数字) — R8 **不警告**（`'回到', '倒退', '前一年', '三年前', '十年前'` 全部是半角字符匹配，全角数字不触发启发式）
- **严重度**: MAJOR（中文用户常输入全角数字 → 倒叙时间不被 R8 检测）
- **修复建议**: R8 的关键词匹配应同时覆盖全角形式。

### A1.6 — `[MAJOR]` `chapter_num=0` 时 R8 时间线检查完全失效

- 实际: `第 1 章` 章节 + `elapsed_time = '回到过去'` → R8 **不警告**（因为 `current_chapter - 1 = 0` 不在 timeline dict 中）
- prev review Test 9.5 已记录。
- **新视角**: 这是 R8 设计**逻辑漏洞** — 第一章本应是"无法判断"的，但实际被完全跳过，连 advisory 都不出。

## 公理 A2：健壮性（新增 + 重大发现）

### A2.1 — `[CRITICAL A2 / A6]` 非 UTF-8 编码章节文件 → 暴露 Python traceback

（详见 A1.1 — 同一发现，但 A2 视角强调"任何输入不能崩溃"）

### A2.2 — `[CRITICAL A2 / A7]` `--db=/etc/passwd` → 暴露 Python traceback

- **推导**: A2 要求"任何输入都不能让系统崩溃"，`/etc/passwd` 是合法文件（`is_file()` 返回 True），但不是 sqlite 数据库 → 触发 `sqlite3.DatabaseError`，**未被 `except sqlite3.OperationalError` 捕获**（父类 vs 子类关系错误）
- **测试**: `python3 changes_gate.py --chapter-file valid.md --db /etc/passwd`
- **实际**:
  ```
  Traceback (most recent call last):
    ...
    File "changes_gate.py", line 288, in _load_entity_lookup
      conn.execute("SELECT 1 FROM entities LIMIT 1")
  sqlite3.DatabaseError: file is not a database
  ```
- **严重度**: **CRITICAL**
- **区别于 prev review Test 12.3**: prev review 测的是"损坏的 sqlite 文件"（同一种错误，但 prev review 误标为已修复）— 实际修复不完整。Top 5 修复建议"加 try/except OperationalError"不够，必须改成 **`except sqlite3.DatabaseError`** 才能覆盖 `file is not a database`。
- **修复建议**: 所有 sqlite loader 的 `except sqlite3.OperationalError` 改为 `except sqlite3.DatabaseError`。

### A2.3 — `[CRITICAL A1 / A6]` 所有"db 无效"路径**静默通过**而非警告

- **推导**: A1（正确性）+ A6（透明性）要求"验证失败时必须告知用户"。当前代码 `_load_entity_lookup` 在 `tables_ok=False` 时返回空 failures，调用方在 `if not tables_ok: return failures`（空 list）→ **R3-R7 全部静默跳过**
- **测试矩阵**（在章节含 NONEXISTENT character_id 的前提下）：

| db 类型 | `passed` | `failures` | R3 捕获 NONEXISTENT? |
|---|---|---|---|
| 缺 `entities` 表 | True | 0 | **否** |
| 缺 `aliases` 表 | True | 0 | **否** |
| 缺两个表 | True | 0 | **否** |
| 空 sqlite（仅 header） | True | 0 | **否** |
| 缺 `current_json` 列 | True | 0 | **否** |
| 缺 `type` 列 | True | 0 | **否** |
| `/dev/null` | True | 0 | **否** |
| `/dev/zero` | True | 0 | **否** |
| `/dev/random` | True | 0 | **否** |
| 破损符号链接 | True | 0 | **否** |

- **严重度**: **CRITICAL**（用户传错的 db → 门禁报告"通过"但实际未做实体/伏笔/物品校验 → 真正的违规悄悄通过）
- **A7 角度**: 攻击者可构造 `/dev/zero` 类文件使门禁永远 pass
- **修复建议**: 当 `tables_ok=False` 时，必须添加 R0 advisory 失败，告知用户"db 不可用，R3-R7 已跳过"

### A2.4 — `[MAJOR A2]` 100MB 章节文件未报错 / 未分块

- 测试: text_humanizer 对 100MB 文件 → 单进程 22.92s 完成，输出 835 字节 JSON
- **问题**: 用户可能不知章节巨大，处理时间会卡住 shell。**无超时、无分块、无进度提示**
- **严重度**: MAJOR（前端 LLM 工具链场景可能产生大文件）

### A2.5 — `[MAJOR A2 / A6]` humanizer 对 binary 文件返回 `ok: true`

- 测试: 6005 字节 binary 内容 → 解析为文本，输出 `char_count: 6005`，`paragraph_count: 1`
- prev review Test 11.4 提到 check-ai-patterns 对 binary 不崩溃，但 humanizer 这里**完全当文本处理且不警告**
- **严重度**: MAJOR（A6 透明性违反 — 误把 binary 当文本，给出"low severity"假结论）

### A2.6 — `[MINOR A2]` text_humanizer 缺 --chapter-file 时 argparse 退出码 2

- prev review 未覆盖；信息层级为 INFO。但需注意 `python3 text_humanizer.py` 没子命令时也 rc=2（usage 错误）。

### A2.7 — `[MINOR A2]` NUL 字节 / BEL / ESC 字符在章节文件中 — 系统未崩溃

## 跨公理综合分析

### 模式 1: 静默失败（Silent Failure Cluster）

**A2 + A6 + A7 共同根因**: 当 db 不可用时（任何 `tables_ok=False` 路径），代码**完全跳过** R3-R7 而**不告知用户**。

| 触发路径 | A2 | A6 | A7 |
|---|---|---|---|
| `--db` 是目录 | 静默通过 | 无警告 | 可被利用 |
| `--db` 是 `/dev/null` / `/dev/zero` / `/dev/random` | 静默通过 | 无警告 | **可被攻击者利用** |
| `--db` 是破损符号链接 | 静默通过 | 无警告 | 可被利用 |
| `--db` 是 socket | 静默通过 | 无警告 | 可被利用 |
| db 文件存在但缺 `entities` 表 | 静默通过 | 无警告 | — |
| db 文件存在但缺 `aliases` 表 | 静默通过 | 无警告 | — |
| db 文件存在但 sqlite header only | 静默通过 | 无警告 | — |
| `--db` 是非 sqlite 文件（如 `/etc/passwd`） | **崩溃** | 暴露 traceback | — |

**修复策略**: `_load_entity_lookup` / `_load_foreshadowing_state` / `_load_item_state` / `_load_timeline` 必须区分 3 种状态：
1. **db 缺失 / 不可用** → 返回 `tables_ok=False` 且调用方必须**添加 R0 advisory 失败**
2. **db 存在但表缺失** → 同上
3. **db 正常但空数据** → 继续校验（已正确处理）

### 模式 2: 输入边界 → 崩溃 + 暴露内部（A2 + A6 共同）

| 触发 | 输出 | 严重度 |
|---|---|---|
| 章节文件是 UTF-16 / GBK / 截断 UTF-8 | Python traceback | CRITICAL |
| `--db` 是非 sqlite 文件 | Python traceback | CRITICAL |
| `--db` 是损坏 sqlite | Python traceback | CRITICAL |

**修复策略**: 所有文件读取 + 数据库连接必须包裹 `try/except UnicodeDecodeError` / `try/except sqlite3.DatabaseError`，并转译为 R0 blocking 错误消息。

### 模式 3: A1 + A6 错误位置信息缺失

- 所有 failure 的 `location` 字段都是 `""`
- 用户无法定位错误在章节文件中的具体位置
- prev review 未提出
- **修复建议**: 在 `Failure` dataclass 中填入 `f"{chapter_file}:line{approx_line}:col{approx_col}"`，其中 line/col 从 JSON 解析错误的 `pos` 字段推算

### 模式 4: R6（去 AI 味）的窗口化问题不是新发现但仍是系统性缺陷

- prev review 已识别 CRITICAL bug #4
- 本次测试再次确认：260+ 误报（`张三李四...` 实际 14 个名字报 131 个）
- **新增视角**: 即使在默认禁用下，开发者仍可能在 CI 中设 `WEBNOVEL_ENABLE_R6=1` 做质量检查 → 误报导致假阳性太多 → 用户禁掉整个 R6
- **建议**: 改进 `extract_chapter_entities` 加入最长匹配优先 + 标点切分

### 模式 5: humanizer 与 check-ai-patterns.js 的差异

- humanizer 对 binary 文件输出 `ok: true`（**不警告**）
- check-ai-patterns 对 binary 文件输出 long-paragraph advisory（**有警告**）
- 两个工具有**不同的人性化策略** — humanizer 应该至少在 binary 输入时输出 warning

## Top 5 优先级修复（基于第一性原理）

1. **(CRITICAL A2/A6/A7)** db 路径必须做 3-态区分（缺失/无效/有效），无效时**必须**添加 R0 advisory 失败。当前静默通过是攻击向量 + 用户体验双输。

2. **(CRITICAL A2/A6)** `Path.read_text(encoding="utf-8")` 必须包裹 `try/except UnicodeDecodeError`，转译为 R0 错误消息。`text_humanizer._load_chapter` 已有正确实现可参考。

3. **(CRITICAL A2/A6)** 所有 sqlite loader 的 `except sqlite3.OperationalError` 改为 `except sqlite3.DatabaseError` — 父类才能捕获 `file is not a database`。当前修复不完整（prev review Top 1 修复建议不够）。

4. **(MAJOR A6)** failure 的 `location` 字段应填充 `chapter_file:line:col`，否则用户无法定位错误。

5. **(MAJOR A2/A6)** humanizer 对 binary 输入应至少返回 `ok: false` + 警告，不应静默通过。

## 结论

第一性原理审查比类别审查**揭示了 6 个未被识别**的 CRITICAL 问题：

1. **UTF-16/GBK/截断 UTF-8 编码章节文件 → 系统崩溃 + traceback 泄露**
2. **`--db=/etc/passwd` 等非 sqlite 文件 → 系统崩溃 + traceback 泄露**
3. **db 无效（缺表/特殊文件/破损链接）→ R3-R7 静默跳过 + silent pass**
4. **`--rule` 参数被 argparse 拒绝而非 deprecation warning**
5. **failure 的 `location` 字段始终为空字符串**
6. **humanizer 对 binary 文件静默通过**

这些发现的**共同特征**：prev review 关注**已知攻击模式**（JSON 类型错误、SQLite 损坏等），第一性原理关注**系统边界**（任何输入不能崩溃、用户必须被告知失败、特殊文件可被构造攻击）。两类审查**互补**而非重复。

建议立即修复 Top 5 优先级，特别是**模式 1（静默失败集群）** — 这不仅是 soundness 问题，更是**安全漏洞**（攻击者可构造特殊文件使门禁永远 pass）。
